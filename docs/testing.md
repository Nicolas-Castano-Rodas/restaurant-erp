# Pruebas integrales (8.6)

CI ejecuta migraciones, 11 pruebas de integración, contraste de tokens, lint, tipos, compilación, HTTP y Playwright Chromium. Las pruebas de navegador usan una base PostgreSQL local llamada restaurant_erp_test y RUN_BROWSER_TESTS=true; se rechazan otros destinos. Generan una organización ficticia independiente y credenciales aleatorias, sin capturas, trazas ni videos que contengan sesiones. El entorno CI es desechable; si se usa localmente, eliminar la base dedicada cuando ya no se necesite (nunca la base de trabajo). Las pruebas verifican inicio de sesión, selección de sucursal, menú móvil, cuatro anchos del dashboard, POS móvil, preparación, consumo de receta, cobro, conciliación, descarga Excel/PDF, auditoría, cierre de sesión y acceso denegado a un rol mesero. Axe comprueba seis reglas semánticas en login; no es auditoría WCAG completa.

Local: crear una base separada restaurant_erp_test, configurar DATABASE_URL hacia ella en una terminal aislada, ejecutar npm install, npm run db:deploy, npm run build, npx playwright install chromium, habilitar RUN_BROWSER_TESTS=true y npm run test:e2e. No iniciar contra restaurant_erp_dev ni producción. No reutilizar un servidor que ya esté corriendo en el puerto 3100. El reporte HTML local está ignorado por Git. Las pruebas no validan Safari/Firefox ni lectores de pantalla reales, ni carga masiva; esas verificaciones siguen como puertas de salida.

El runner de Playwright no importa el cliente Prisma en tiempo de ejecución. El guard de la base desechable es independiente; la creación de fixtures y lectura de saldos/cobros se ejecutan en un proceso Node con tsx, igual que las pruebas de integración. Las contraseñas ficticias se pasan por entorno y no por argumentos. No se cambia el formato del cliente Prisma de producción.

Validación de referencia e7d786d (run 45688669694): las 11 suites de integración, 21 comprobaciones de contraste, lint, tipos, build, HTTP y dos pruebas Chromium pasaron. Esto no sustituye la restauración de backups gestionados en staging ni pruebas de carga. El informe de vulnerabilidades altas pasa a ser un job bloqueante independiente; no confundir resultado funcional con seguridad.
